network 模块

🌐 network — 网络物理层

阶段二核心：Packet / Link / Switch / Drop 四大构件，构建可模拟的物理网络

子模块划分

文件职责
packet.rsPacket 结构、MTU、PacketKind、RDMA 扩展字段
link.rs单向链路、序列化延迟（整数运算）、LinkRegistry
switch.rs多端口交换机、优先级队列、PFC、ECN、路由
drop.rs丢包原因枚举、逐流/逐端口/分原因统计
host_delay.rs主机内部硬件延迟模型（NVLink/PCIe/DMA）

核心设计原则

  • 单向链路：一条物理链路 = 两条单向 Link，发送与接收独立建模
  • 整数运算：序列化延迟 (bytes * 8 * 1e9) / bw_bps，全 u64 避免浮点
  • 最小公共包：Packet 只保留各协议共有的最小字段，扩展通过 payload 编码
  • 多优先级：交换机端口支持 NUM_PRIORITIES=2 个队列（0=高优先级）
PFC（Priority Flow Control）在交换机端口队列超过阈值时向上游发送 pause 帧，模拟真实无损以太网行为。

Packet 结构与 RDMA 扩展

Packet 第一字段始终是 id，事件流转时只携带 packet_id 避免大量拷贝。

pub struct Packet { pub id: PacketId, // slab 索引（SimRunner 分配） pub kind: PacketKind, // Data | Control(u8) pub flow_id: FlowId, pub seq: SeqNum, pub size: u32, // Data 默认 MTU=1024B, Control=64B pub src, dst: EntityId, pub ecn: bool, // 拥塞标记（交换机 ingress 打标） pub routing_tag: u8, // 路径选择 / 优先级编码 pub payload: Vec<u8>, // 协议扩展数据（如 SACK bitmap） pub depart_time: u64, // 真实 NIC 出主机时间（用于 RTO） pub trace_id: PacketId, // 全局唯一追踪 ID（P1 可观测性） // RDMA 扩展字段（向下兼容：非 RDMA 包全为 0） pub qpn: u32, psn: u32, pub msg_flags: u8, pub rdma_opcode: u8, }
routing_tag 的双重用意：低 bits 用于 ECMP/Spraying 路径选择（1-based 索引）；≥128 表示高优先级（映射到交换机端口的高优先级队列）。

Link 模型：序列化延迟

链路是单向的，用 link_busy_until: Vec<u64> 数组建模"一次只能发一个包"的物理约束。

Link 结构

pub struct Link { pub id: LinkId, pub from: EntityId, pub to: EntityId, pub bandwidth_bps: u64, // 如 100_000_000_000 = 100Gbps pub prop_delay_ns: u64, // 传播延迟（ns） } // 整数运算，零浮点 pub fn serialization_ns(&self, size_bytes: u32) -> u64 { (size_bytes as u64 * 8 * 1_000_000_000) / self.bandwidth_bps }

LinkRegistry

pub struct LinkRegistry { links: Vec<Link>, } pub fn add(&mut self, mut link: Link) -> LinkId { let id = self.links.len() as LinkId; link.id = id; self.links.push(link); id } // O(1) 索引 pub fn get(&self, id: LinkId) -> &Link { &self.links[id as usize] }
Dense array indexing 替代 HashMap，缓存友好且零哈希开销。

Switch 模型：Ingress / Egress / PFC

交换机是多端口设备，每个端口包含 NUM_PRIORITIES=2 个 FIFO 子队列。核心行为在 ingress() 中完成。

pub fn ingress(&mut self, mut pkt: Packet, hash_key: u32, now: u64) -> (Option<PortId>, bool) { // 1. 路由查找 let ports = self.routing.ports_for(pkt.dst)?; let chosen = if pkt.routing_tag > 0 { pkt.routing_tag - 1 // STrack 显式指定路径 } else { hash_key as usize % ports.len() // ECMP 流哈希 }; // 2. Buffer 满 → 丢包（记录原因、端口、流、时间） if port.queue_bytes + pkt_size > self.buffer_max_bytes { self.drop_counters.record(DropReason::BufferFull, ...); return (Some(chosen), true); } // 3. ECN 阈值 → 打标 if port.queue_bytes + pkt_size > self.ecn_threshold_bytes { pkt.ecn = true; self.ecn_marks += 1; } // 4. 根据 routing_tag 选择优先级并入队 let priority = if pkt.routing_tag >= 128 { HIGH_PRIORITY } else { LOW_PRIORITY }; port.enqueue_priority(pkt, priority); // 5. PFC：检查是否触发 pause if port.check_pfc(priority) { self.pfc_pause_sent += 1; } (Some(chosen), false) }
Egress 由 SimRunner 的 try_egress() 驱动：端口空闲时 dequeue，否则调度 PacketDepart 事件在未来重试。这实现了物理链路的串行化。

丢包归因与主机延迟模型

DropCounters：多维统计

pub struct DropCounters { pub by_reason: [u64; 4], // NoRoute / BufferFull / Ttl / Other pub by_port: Vec<u64>, // 逐端口 pub total: u64, pub per_flow: HashMap<FlowId, PerFlowDrops>, pub events: Vec<DropEvent>, // 详细日志（可选） }

替代了早期简单的 drops: u64，支持诊断"哪条流在哪台交换机的哪个端口因何丢包"。

HostDelayModel：GPU → NIC 延迟

pub struct HostDelayModel { dma_bw_bps: u64, // 0 = 零拷贝（RDMA） doorbell_ns: u64, // ~200ns pcie_roundtrip_ns: u64, // ~500ns kernel_stack_ns: u64, // TCP 场景 ~2μs memcpy_bw_bps: u64, // 用户态→内核拷贝带宽 rx_interrupt_ns: u64, // 接收中断 cq_poll_ns: u64, // CQE 轮询 }

提供三种预设：rdma_zerocopy()、rdma_with_staging()、tcp_kernel()。

主机延迟通过 SimRunner 的 host_tx_busy_until 实现 DMA 引擎串行化，多流争用同一 DMA 引擎时会排队。

测试覆盖与关键断言

switch.rs 单元测试

  • no_route_drops：无路由时正确丢包并计数
  • ecn_marks_above_threshold：队列超阈值后第二个包被打 ECN 标记
  • drops_when_buffer_full：Buffer 满后后续包被丢弃
  • ecmp_hash_distributes：300 个包均匀分散到 3 个端口
  • routing_tag_overrides_ecmp：显式 routing_tag 可覆盖哈希

link.rs / drop.rs 测试

  • serialization_at_100gbps：1024B @ 100Gbps ≈ 81.92 ns
  • arrive_time_includes_propagation：总延迟 = serialization + prop_delay
  • DropCounters：record 后按原因、端口、流三维统计正确
所有测试均在模块内部以 #[cfg(test)] 组织，cargo test --release 时一并执行。
